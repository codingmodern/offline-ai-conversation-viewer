### Dependency Justifications

- **React**: مدیریت پیچیدگی UI چندحالته (چند Theme، چند مکالمه، Sidebar پویا) با یک مدل Component-based شناخته‌شده.
- **Vite**: Build سریع، Dev Experience خوب، خروجی بهینه و کاملاً استاتیک — سازگار با محدودیت "بدون بک‌اند".
- **Dexie.js**: API سطح بالا روی IndexedDB با پشتیبانی از Query، Index، و Transaction — مناسب برای کتابخانه‌ای با تعداد نامشخص مکالمه و جستجو.
- **CSS Modules + Custom Properties**: جداسازی کامل استایل هر پلتفرم (Theme) بدون تداخل، در حالی که Tokenهای پایه (رنگ، فونت، Radius) در سطح متغیرهای CSS تعریف و در `ui-context.md` مستند می‌شوند.
- **TypeScript**: چون هر پلتفرم ساختار JSON متفاوتی دارد، Type Safety به‌شدت به جلوگیری از خطا در لایه‌ی Parsing کمک می‌کند.

## 2. System Architecture

### Architecture Pattern

- **Pattern:** Layered Client-Side Architecture (Modular Plugin Pattern برای Parserها)
- **Rationale:** چون هیچ بک‌اندی وجود ندارد، تمام لایه‌ها (Parsing، Storage، Rendering) در مرورگر اجرا می‌شوند. الگوی Plugin برای Parserها تضمین می‌کند افزودن پلتفرم جدید بدون تغییر کد موجود ممکن باشد (Open/Closed Principle).

### System Boundaries

```
src/
├── parsers/            — یک ماژول مستقل به‌ازای هر پلتفرم (chatgpt, claude, gemini, deepseek)
├── detection/           — منطق تشخیص خودکار پلتفرم از روی ساختار JSON
├── normalization/       — تبدیل خروجی هر Parser به یک مدل داده‌ی یکسان (Unified Conversation Model)
├── storage/             — لایه‌ی Dexie.js: Schema، Query، CRUD کتابخانه‌ی مکالمات
├── themes/              — یک ماژول Theme مستقل به‌ازای هر پلتفرم (CSS Modules + Tokens)
├── components/          — کامپوننت‌های مشترک (Sidebar, Search, Layout)
├── features/            — منطق ویژگی‌ها (Import, Library, Search, Metadata Panel)
├── types/               — تعریف مدل‌های داده و Interfaceهای مشترک
└── workers/             — Web Worker برای Parse فایل‌های حجیم بدون Block کردن UI
```

| Folder / Module  | Responsibility                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| `parsers/`       | Parse خام هر فرمت JSON به داده‌ی خام مخصوص همان پلتفرم؛ کاملاً مستقل از سایر Parserها                   |
| `detection/`     | بررسی امضای ساختاری فایل JSON و تعیین پلتفرم مبدا، بدون دخالت کاربر                                     |
| `normalization/` | نگاشت داده‌ی خام هر پلتفرم به یک مدل واحد (`UnifiedConversation`) که UI و Storage از آن استفاده می‌کنند |
| `storage/`       | تعریف Schema Dexie، عملیات ذخیره/بازیابی/حذف در IndexedDB                                               |
| `themes/`        | تعریف Token‌ها، Layout و کامپوننت‌های بصری اختصاصی هر پلتفرم                                            |
| `components/`    | Sidebar، نوار جستجو، Layout عمومی، پنل متادیتا                                                          |
| `features/`      | Orchestration ویژگی‌ها (مثلاً جریان کامل Import → Detect → Normalize → Save)                            |
| `workers/`       | اجرای Parse سنگین در Thread جداگانه برای جلوگیری از Freeze شدن UI                                       |

### Internal Module Contracts (به‌جای API Design — پروژه بدون بک‌اند/REST است)

| Aspect                               | Decision                                                                                                                                                                                                                                                                                               |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **ارتباط بین لایه‌ها**               | فراخوانی تابع مستقیم (In-process)؛ بدون HTTP، بدون Network                                                                                                                                                                                                                                             |
| **قرارداد هر Parser**                | هر ماژول در `parsers/` باید یک تابع با امضای ثابت پیاده‌سازی کند: `detect(rawJson): boolean` و `parse(rawJson): UnifiedConversation`                                                                                                                                                                   |
| **Registry واحد**                    | تمام ماژول‌های `parsers/` در یک Registry مرکزی (`detection/registry.ts`) ثبت می‌شوند؛ لایه‌ی Detection برای `detect()` و لایه‌ی Parsing برای `parse()` از همین یک Registry استفاده می‌کنند — هیچ Registry موازی مجاز نیست. راهنمای افزودن پلتفرم: `docs/parsers.md`                                    |
| **مدل داده‌ی مشترک**                 | تمام Parserها خروجی خود را به `UnifiedConversation` (تعریف‌شده در `types/`) نگاشت می‌کنند؛ لایه‌های بالاتر (UI، Storage، Search) فقط با این مدل کار می‌کنند                                                                                                                                            |
| **انواع پیام در مدل مشترک**          | `UnifiedMessage` یک Discriminator به‌نام `kind` دارد (`text` / `attachment` / `tool_activity`)؛ به‌ازای هر `kind` فقط Payload متناظر پر می‌شود (`content` / `attachments` / `toolActivity`) و `sourceFragmentType` نوع خام پلتفرم (مثلاً `THINK`, `TOOL_OPEN`) را برای وفاداری و رندر آینده حفظ می‌کند |
| **پاسخهای جایگزین یک نوبت**         | `UnifiedMessage.alternatives?: readonly string[]` — فیلد اختیاری برای پاسخهای **جایگزین** (نه پیامهای جدا) یک نوبت؛ فقط Gemini (Unit 10) آن را پر میکند، و فقط وقتی نوبت واقعاً بیش از یک پاسخ دارد (Draftهای چندگانه). در Claude/DeepSeek همیشه غایب است، پس مصرفکنندههای موجود دستنخورده میمانند (ADR #25) |
| **فیلد حیاتی، وابسته به `kind` است** | «حیاتی بودن» یک فیلد مطلق نیست: `content` فقط برای `kind === 'text'` و `files` فقط برای `kind === 'attachment'` باعث `MissingFieldError` می‌شود؛ `results` هرگز حیاتی نیست                                                                                                                             |
| **خطا در Parse/Detect**              | هر ماژول خطای خودش را با نوع `ParseError` مشخص برمی‌گرداند؛ لایه‌ی Import این خطاها را به پیام قابل‌فهم برای کاربر تبدیل می‌کند                                                                                                                                                                        |

### Data Flow

```
[کاربر: انتخاب/Drag فایل] → [Import Layer: خواندن فایل]
        → [Web Worker: Parse خام JSON]
        → [Detection Layer: تشخیص پلتفرم]
        → [Parser مربوطه: تبدیل به داده‌ی خام Provider]
        → [Normalization Layer: تبدیل به UnifiedConversation]
        → [Storage Layer: ذخیره در IndexedDB via Dexie]
        → [UI: به‌روزرسانی Sidebar کتابخانه]
        → [کاربر: انتخاب مکالمه] → [Theme Layer: رندر با UI اختصاصی پلتفرم]
```

- کل جریان به‌صورت Synchronous در مرورگر انجام می‌شود؛ Parse فایل‌های بزرگ در Web Worker اجرا می‌شود تا از Freeze شدن رابط کاربری جلوگیری شود.
- هیچ نقطه‌ای از این جریان درخواست شبکه‌ای ارسال نمی‌کند.

## 3. Storage Model

| Storage Type                | What Lives Here                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------------------------- |
| **IndexedDB (via Dexie)**   | کتابخانه‌ی مکالمات (`UnifiedConversation[]`)، متادیتای هر مکالمه، ایندکس‌های جستجو                        |
| **In-Memory (React State)** | مکالمه‌ی در حال نمایش، وضعیت UI (فیلتر جستجو، Sidebar باز/بسته)                                           |
| **File / Blob Storage**     | استفاده نمی‌شود — فایل ورودی فقط در حافظه Parse و سپس دور ریخته می‌شود؛ فقط داده‌ی نرمال‌شده ذخیره می‌شود |

> نکته: فایل خام JSON کاربر ذخیره نمی‌شود، فقط خروجی Normalize‌شده. این تصمیم باید در ADR ثبت شود (بخش پایین).

### Dexie Schema (پیاده‌سازی‌شده در Unit 04)

پایگاه داده `offline-ai-conversation-viewer`، نسخه‌ی schema `1`، تنها یک جدول دارد:

```
conversations: '++id, platform, importedAt, [platform+sourceConversationId]'
```

| Field                  | Indexed    | Why                                                                                                                            |
| ---------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `id`                   | PK         | کلید جانشین (surrogate) و auto-increment — کلید طبیعی نمی‌تواند PK باشد چون «Add anyway» باید نسخه‌ی دوم را ذخیره کند (ADR #9) |
| `platform`             | ✅         | Query helper برای جستجوی هر پلتفرم (FR1)                                                                                       |
| `importedAt`           | ✅         | کلید مرتب‌سازی Sidebar؛ ایندکس‌شده تا ترتیب توسط IndexedDB انجام شود، نه با خواندن همه‌ی رکوردها                               |
| `sourceConversationId` | (compound) | همراه `platform` تشکیل‌دهنده‌ی کلید تشخیص تکراری                                                                               |
| `conversation`         | ❌         | کل `UnifiedConversation` عیناً؛ ایندکس‌نشده تا نوشتن Export‌های بزرگ ارزان بماند                                               |

ایندکس مرکب `[platform+sourceConversationId]` عمداً **unique نیست** (`&` ندارد): یکتایی در سطح موتور، «Add anyway» را غیرممکن می‌کرد.

**قواعد لایه‌بندی (FR2/FR3):**

- فقط `src/storage/` مجاز است Dexie/IndexedDB را مستقیماً import کند. کامپوننت‌ها و hook‌ها از طریق `conversationStore.ts` کار می‌کنند، پس فناوری ذخیره‌سازی قابل تعویض می‌ماند.
- هر نوشتن یک تراکنش اتمیک Dexie است (`db.transaction('rw', …)`): تشخیص تکراری و درج در **یک** تراکنش انجام می‌شوند تا بین بررسی و نوشتن، شرط مسابقه (race) رخ ندهد. پاک‌سازی کامل کتابخانه (`clearLibrary`) نیز یک تراکنش اتمیک مجزاست (ADR #14).
- خطاها به‌صورت `StorageResult<T>` برمی‌گردند (همان الگوی `Result` واحد ۰۱–۰۳)، هرگز throw نمی‌شوند.

## 5. Non-Functional Requirements

### Performance

| Metric                                        | Target                                        |
| --------------------------------------------- | --------------------------------------------- |
| **Time to Parse a Typical Export (<5MB)**     | < 1s                                          |
| **Time to Parse a Large Export (up to 50MB)** | < 5s، در Web Worker، بدون Block شدن UI        |
| **Sidebar Render با ده‌ها مکالمه**            | < 200ms                                       |
| **جستجو در محتوای مکالمات**                   | نتیجه در کمتر از 300ms برای کتابخانه‌ی معمولی |

### Security

| Requirement          | Implementation                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **حریم خصوصی داده**  | هیچ داده‌ای هرگز از مرورگر خارج نمی‌شود؛ بدون هیچ درخواست شبکه‌ای                                                                                                                    |
| **Input Validation** | هر Parser ساختار JSON را قبل از پردازش با Type Guard/Schema بررسی می‌کند                                                                                                             |
| **XSS Protection**   | محتوای پیام‌ها (که ممکن است HTML/Markdown خام از پلتفرم مبدا باشد) قبل از رندر Sanitize می‌شود (مثلاً با DOMPurify)؛ هرگز با `dangerouslySetInnerHTML` بدون Sanitize استفاده نمی‌شود |
| **Storage Quota**    | بررسی نزدیک شدن به سقف Quota مرورگر و اطلاع‌رسانی به کاربر پیش از خطای Storage                                                                                                       |

### Scalability

| Aspect                                 | Strategy                                                                                                                                                                                                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **تعداد زیاد مکالمه در کتابخانه**      | **به تعویق افتاده (Unit 04 / NFR2).** Sidebar فهرست را ساده رندر می‌کند. List Virtualization فقط در صورتی اضافه می‌شود که داده‌ی واقعی کندی را نشان دهد — بهینه‌سازی پیش‌دستانه، پیچیدگی بی‌دلیل است (اصل spec-cleanliness) |
| **پیام‌های بسیار طولانی در یک مکالمه** | Virtualized Scrolling در پنجره‌ی چت — تصمیم آن به Unit 06 (رندر محتوا) واگذار می‌شود، با همان قاعده‌ی «اول اندازه‌گیری»                                                                                                     |

### Reliability

| Aspect             | Strategy                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| **Error Handling** | خطای Parse/Detect هرگز باعث Crash کل اپ نمی‌شود؛ فقط همان فایل رد می‌شود با پیام مشخص             |
| **Logging**        | لاگ خطا فقط در Console مرورگر (بدون ارسال به هیچ سرویس خارجی)                                     |
| **Monitoring**     | موضوعیت ندارد (بدون سرور)                                                                         |
| **Backup**         | مسئولیت کاربر است؛ می‌تواند در آینده قابلیت Export/Backup کتابخانه اضافه شود (خارج از Scope فعلی) |

## 6. Invariants

> این قوانین هرگز نباید نقض شوند.

1. **هیچ درخواست شبکه‌ای در هیچ نقطه‌ای از اپلیکیشن ارسال نمی‌شود.** (بدون Fetch، بدون API خارجی، بدون CDN در Runtime)
2. **تمام پردازش (Parse، Detect، Search، Render) در سمت کلاینت و داخل مرورگر انجام می‌شود.**
3. **ماژول‌های `parsers/` هرگز به یکدیگر وابستگی مستقیم ندارند.** افزودن یا تغییر یک Parser نباید Parser دیگری را تحت تأثیر قرار دهد.
4. **تشخیص پلتفرم همیشه خودکار است؛ هیچ UI برای انتخاب دستی پلتفرم وجود ندارد.**
5. **محتوای رندرشده از فایل ورودی همیشه قبل از نمایش Sanitize می‌شود.**
6. **هیچ کد یا Asset اختصاصی/رسمی از پلتفرم‌های اصلی (ChatGPT, Claude, Gemini, DeepSeek) در پروژه کپی نمی‌شود؛ Themeها بازآفرینی مستقل هستند.**

## 7. Constraints & Edge Cases

### Technical Constraints

| Constraint                                                                                   | Impact                                                                                                                                  |
| -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| سقف حجم IndexedDB بسته به مرورگر متغیر است                                                   | باید هشدار نزدیک‌شدن به Quota پیاده‌سازی شود                                                                                            |
| Parse فایل‌های بسیار بزرگ می‌تواند UI را Block کند                                           | استفاده از Web Worker برای Parse اجباری است                                                                                             |
| فرمت‌های رسمی Export ممکن است بدون اطلاع‌رسانی توسط پلتفرم‌ها تغییر کنند                     | معماری Parser ماژولار طراحی شده تا فقط ماژول مربوطه به‌روزرسانی شود                                                                     |
| یک فایل نمونه (Fixture) ممکن است فقط زیرمجموعه‌ای از انواع داده‌ی واقعی پلتفرم را داشته باشد | Fixture هرگز به‌عنوان «فهرست کامل» تلقی نمی‌شود؛ پیش از تعریف یک فیلد به‌عنوان حیاتی، باید Census کامل انواع روی Export واقعی انجام شود |

### Business Rules

| Rule                                   | Description                               |
| -------------------------------------- | ----------------------------------------- |
| فقط فرمت JSON پذیرفته می‌شود (فاز اول) | فایل با پسوند/ساختار غیر JSON رد می‌شود   |
| تشخیص پلتفرم همیشه خودکار است          | هیچ مسیر UI برای Override دستی وجود ندارد |

### Edge Cases

| Scenario                                                                                                                                                  | Expected Behavior                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| فایل JSON نامعتبر یا خراب (Corrupt)                                                                                                                       | پیام خطای واضح؛ فایل به کتابخانه اضافه نمی‌شود؛ اپ Crash نمی‌کند                                                                                                                                                                                                  |
| ساختار JSON ناشناخته (هیچ Parser تطبیق ندارد)                                                                                                             | پیام "Unsupported Format"؛ امکان گزارش/مشاهده جزئیات فنی خطا برای Debug                                                                                                                                                                                           |
| متادیتای ناقص (مثلاً بدون تاریخ یا نام مدل)                                                                                                               | فقط فیلدهای موجود نمایش داده می‌شوند؛ بدون خطا یا مقدار جعلی                                                                                                                                                                                                      |
| فایل تکراری (Import مجدد همان مکالمه)                                                                                                                     | تشخیص تکراری بر اساس شناسه‌ی مکالمه (در صورت وجود در فایل) و هشدار به کاربر پیش از افزودن مجدد                                                                                                                                                                    |
| حجم فایل بسیار بزرگ (>50MB)                                                                                                                               | هشدار پیش از Parse؛ اجرای Parse در Web Worker با نمایش Progress                                                                                                                                                                                                   |
| پر شدن Storage Quota مرورگر                                                                                                                               | پیام خطای واضح؛ پیشنهاد حذف مکالمات قدیمی                                                                                                                                                                                                                         |
| یک Fragment که Payload آن `content` نیست (DeepSeek: `FILE` با `files`، و `SEARCH`/`TOOL_SEARCH`/`TOOL_OPEN`/`TOOL_FIND` با `results` یا بدون هیچ Payload) | بر اساس دسته‌ی Fragment نگاشت می‌شود، نه با فرض «`content` همیشه اجباری است»: `kind` برابر `attachment` یا `tool_activity` می‌شود و نبود `content` خطا نیست. تحمیل `content` به‌عنوان فیلد حیاتی جهانی، باعث `MissingFieldError` و رد شدن کامل Export واقعی می‌شد |
| Fragment از نوع `SEARCH`/`TOOL_SEARCH` که `results` دارد، در مقابل `TOOL_OPEN`/`TOOL_FIND` که ندارند                                                      | `results` هرگز فیلد حیاتی نیست؛ در صورت وجود، Payload خام و دست‌نخورده حفظ می‌شود و در صورت نبود، فیلدی ساخته/جعل نمی‌شود                                                                                                                                         |
