### ADR #35 — ChatGPT visibility filter runs in parser and normalization; hidden ancestors still feed FR-9 (Unit 11a)

**Decision:** In the ChatGPT provider (Unit 11a), the FR-5 visibility filter (system
role, hidden messages, weight 0, editable-context types) is applied in the parser AND
again in normalization. The parser drops those messages from the thread but their
timestamps still feed FR-9 time inheritance.

**Context:** FR-9 requires a message with no own `create_time` to inherit the nearest
ancestor **on the active branch** that carries one — including ancestors the user never
sees (system prompt, hidden assistant messages, zero-weight regenerates, editable
context). Those ancestors carry the only clock a displayed message may legally inherit,
so dropping them before the inheritance walk would collapse the whole thread onto the
conversation-level `create_time` and mis-order every undated message.

**Rationale:** The parser must keep the full node chain to inherit times from hidden
ancestors; normalization keeps the filter as a safety net. Walking only the already-
displayed list would make `zero.create_time = 1750000202` invisible to `u1`, leaving it
with no time at all. The one-pass assembly in `buildMessages` therefore reads
`ownTime` for every node on the resolved branch and emits only `isDisplayedMessage`
results — structural/timing data flows through both steps.

**Consequences:**

- The parser emits 3 messages for the `structure` fixture (u1, a1, a2) while walking 8
  nodes for time inheritance — exactly the FR-9 chain the spec demands.
- Normalization re-applies the FR-5 filter as defense-in-depth; a regression that
  let a hidden/context message reach it cannot change the displayed thread.

**Files Created / Modified (Unit 11a):**

- `src/parsers/chatgpt/parse.ts` — `buildMessages` reads `ownTime` before the display
  filter; new `isDisplayedMessage` helper gates emission only.

### ADR #19 — In-Chat Search (full-library text search)

**Date:** 2026-08-27 · **Status:** Accepted · **Deciders:** user (pre-approved) + implementer (two noted implementation choices)

**Context:** The user can now hold many saved conversations; finding one by title alone is insufficient. The spec (`07-in-chat-search.md`) requires matching title + message content across the whole library, surfacing matching conversations, with selection reusing the existing `selectConversation` path (FR4) — no new navigation, no auto-scroll, no highlighting.

**Decisions:**

1. **Searchable content scope (pre-approved).**
   - `kind: 'text'` message `content` is searchable (ADR #7 — REQUEST/RESPONSE/THINK).
   - `kind: 'attachment'` `fileName` is searchable — finding a conversation by a remembered attached file's name is real user value at negligible cost.
   - `kind: 'tool_activity'` payloads are **never** read by the index. Their only payload is `results`, whose inner shape is undocumented (ADR #18), and searching it would mean parsing an undocumented structure — inventing product behaviour.

2. **Performance architecture (pre-approved): in-memory index, no per-keystroke Dexie scan.** The reference library (real DeepSeek export) has 133 conversations; reading full records on every keystroke would violate NFR1 (300 ms) and NFR3 (non-blocking UI). The chosen shape is a derived `SearchIndexEntry[]` re-projected inside the same `liveQuery` Unit 04's `subscribeToLibrary` already uses — a separate `subscribeToSearchIndex` that keeps the Sidebar's `LibraryEntry` clean (no full-text payload) while satisfying FR3 (only `storage/` touches Dexie) by **reusing** the existing storage seam, not opening a second one.

3. **Filtering is synchronous per keystroke (not debounced).** The haystack is case-folded once at index-build time; per-keystroke matching is a single `includes()` pass over pre-folded strings, which is orders of magnitude inside NFR1's 300 ms budget for the 133-conversation reference library (proven by `searchConversations.test.ts → scales far inside NFR1`, which asserts < 300 ms for 20 passes over ~8 MB of synthetic haystack — about 20 the real-world corpus). A debounce would add latency without saving any work, so it is omitted.

4. **Selection path (FR4): reusing the existing mechanism.** A result click calls the Sidebar's existing `onSelect` (already wired to `useLibrary.selectConversation` in `AppShell`). No new path, no new "navigate-to-search-result" route. No auto-scroll-to-message and no highlighting — both explicitly out of scope.

5. **Non-Latin text (Edge Cases): verbatim-after-`toLowerCase()` only.** v1 matches Persian, Arabic, Cyrillic, etc. **verbatim** — `toLowerCase()` is a no-op on caseless scripts, so they survive byte-for-byte. No NFC/ZWNJ/casefold normalisation, no Arabic Yeh/Kaf folding, no hard-vs-soft variation folding. Trade-off: a query typed the way the text was written always matches; cross-spelling look-alikes (`/`, `ك/ک`, hard vs soft ZWNJ) do **not** cross-match. This is the same pitfall family as Unit 05's `\d` vs `[۰-۹]` lesson, accepted for v1, and pinned by a dedicated test (`matches Persian queries verbatim`). Normalisation can be added later as a pure transformation step at index-build time without changing the matcher.

**Consequences:**

- The in-memory index grows with the corpus. At 133 conversations  hundreds of KB each (long Persian threads with code fences) the index is on the order of single-digit megabytes — trivially small. If the corpus ever grows past 100 today's size, the same architecture still holds: the index is re-projected on every change, not rebuilt on every keystroke.
- `tool_activity` is excluded from search. If product later needs "find the conversation where the agent ran a web search for X", that requires first giving `toolActivity` a documented, parseable shape (a separate ADR).
- The Sidebar component gains a single `search` prop. Its tests run without IndexedDB (FR3 unchanged); a tiny no-op factory (`makeNoopSearch()`) lets the existing test suite cover both views with one render.
- A new layer in `features/search/` exists alongside `features/library/`, `features/import/`, etc. — same composition pattern: pure matcher + React hook, no direct Dexie access.

### ADR #22 — Claude message order: sentinel-rooted last-child walk (Unit 09)

**Context:** A real Claude export (2026-09-08 census: 29 conversations, 3380
live-line messages, ~9.9 MB) stores every branch of every regenerate/edit in
one `parent_message_uuid` graph per conversation. Array order mixes dead
siblings into the flow and is not even chronological; a whole subtree (7
attested) can hang off a skipped sibling.

**Decision:**

1. Conversation order is produced by walking the graph from the sentinel root
   (`parent_message_uuid === null`) and, at every branch point, taking the
   **last child in array order** — the newest sibling and the only one whose
   line continues (the live line is exactly one child per node).
2. Branches hanging off skipped siblings are deliberately excluded — that is
   what "last child at every branch point" means. Dead branches are Claude's
   UI-side edit/regenerate history, not part of the conversation.
3. The walk lives in `parse()` (`parsers/claude/parse.ts → orderMessages`);
   `normalization/claude.ts` maps the surviving live line 1:1.

**Consequences:**

- The unified model stays a flat, linear message list — no branch data model
  and no renderer changes anywhere else.
- Stale regenerate content never leaks into the library or search (pinned by
  `tests/normalization/claude.fixture.test.ts`).
- Timestamps are metadata only (`createdAt`/`updatedAt`), never ordering input.
- The hidden+summary thinking variant can only be pinned through an inline
  live-line fixture, because a real export shows it exclusively on dead
  branches this walk never visits.

### ADR #23 — Corrupt Claude parent graphs fail parse; one reachability check subsumes cycle detection (Unit 09)

**Context:** Three corruptions are possible in the wild: two messages sharing
one `uuid`, a `parent_message_uuid` pointing at a message the file does not
define, and a cycle in the parent graph. A cycle would make the last-child walk
non-terminating; an unreachable island would mean messages the export claims to
contain but rendering would silently lose.

**Decision:**

1. `orderMessages()` fails with `UnsupportedFormatError` on duplicate uuids and
   dangling parent references (the missing-parent message names the offending
   `parentKey`).
2. A single BFS reachability pass from the sentinel root runs before the walk;
   any message not reachable through *any* child chain fails the parse with
   `N of M messages are unreachable from the root message tree`. Cycles are
   subsumed: a cycle node's parent is always another cycle node, so every cycle
   is unreachable from the root.
3. The last-child walk then runs on a proven acyclic tree and needs no
   visited-set.

**Consequences:**

- Rendering a truncated conversation is impossible: corruption fails loudly at
  import time, mirroring DeepSeek's rule (ADR #4's spirit) that a partially
  readable export must not silently hide data.
- Dead regenerate branches intentionally pass the reachability check (they hang
  off live nodes) and are dropped by ADR #22's walk — they are not corruption.
