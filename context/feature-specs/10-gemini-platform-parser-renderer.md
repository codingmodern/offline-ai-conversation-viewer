# Spec: Gemini Platform Parser & Renderer

> شماره Unit را مطابق `progress-tracker.md` پروژه خودتان تنظیم کنید (بعد از آخرین Unit تکمیل‌شده).
> منبع تحلیل: فایل واقعی `conversations.json` (Google Takeout — My Activity، ۲۳ آیتم / ۷ مکالمه) + ۳ اسکرین‌شات UI.

---

## 1. Goal

ایمپورت خروجی Google Takeout مربوط به Gemini Apps Activity و نمایش اصیل (Authentic) آن، هم‌راستا با معماری چندپلتفرمی موجود (Claude، و آینده ChatGPT).

---

## 2. Context — یافته‌های ساختاری فایل واقعی

- فرمت منبع **Google Takeout "My Activity" است، نه یک Native Chat Export**.
- هر آیتم آرایه = **یک نوبت گفتگو** (یک پیام کاربر + یک/چند پاسخ مدل)، نه یک شیء کامل مکالمه.
- گروه‌بندی مکالمات فقط از طریق شناسه داخل `details[0].url` امکان‌پذیر است.
- ترتیب آیتم‌ها در فایل (چه در کل فایل، چه داخل هر گروه) **نزولی بر اساس زمان** است.
- پیام کاربر = `title`، با پیشوند ثابت فارسی `"درخواست: "`.
- پاسخ مدل = `safeHtmlItem[].html` — **HTML از قبل رندرشده** (نه Markdown خام).
- بعضی آیتم‌ها بیش از یک عضو در `safeHtmlItem` دارند (Draftهای چندگانه Gemini).
- پیوست‌ها (`attachedFiles`, `imageFile`, `subtitles`) فقط **نام فایل** را دارند؛ باینری در این export موجود نیست.
- فیلدهای `header`, `products`, `activityControls` ثابت و بدون اطلاعات کاربردی‌اند.
- هیچ `id`، `role`، یا `model` (مثلاً Flash/Pro) در سطح پیام وجود ندارد.
- هیچ عنوان مستقلی برای مکالمه ذخیره نشده (برخلاف نمای واقعی سایدبار Gemini).

### تصمیمات معماری ثبت‌شده (توسط کاربر تأیید شده)
| تصمیم | انتخاب |
|---|---|
| رندر HTML پاسخ مدل | مستقیم با DOMPurify sanitize — **بدون** عبور از pipeline مشترک `marked` |
| Draftهای چندگانه | نمایش با دکمه جابجایی بین Draftها (نه فقط پاسخ اول) |
| نمایش تاریخ پیام | میلادی (Gregorian) — هم‌راستا با Claude/ChatGPT؛ تبدیل به شمسی در آینده فقط در لایه نمایش |
| عنوان مکالمه در لیست | مشتق‌شده از اولین پیام کاربر همان مکالمه (کوتاه‌شده) |
| پیشوند `"درخواست: "` | حذف می‌شود؛ به‌عنوان ثابت مخصوص همین export مستند می‌شود، نه قاعده عمومی چندزبانه |
| پیوست بدون باینری | نمایش Placeholder (آیکون + نام فایل)، بدون تلاش برای بارگذاری فایل واقعی |

---

## 3. User Flow

1. کاربر فایل `conversations.json` مربوط به Gemini را از طریق مکانیزم ایمپورت موجود انتخاب می‌کند.
2. اپ فرمت را به‌عنوان Gemini Takeout تشخیص می‌دهد (توسعه منطق Format Detection موجود).
3. Parser آیتم‌ها را بر اساس URL مکالمه گروه‌بندی، مرتب‌سازی زمانی صعودی، و عنوان مکالمه را استخراج می‌کند.
4. مکالمات در بخش Gemini لیست پلتفرم‌ها ظاهر می‌شوند.
5. با انتخاب یک مکالمه، پیام‌ها با ظاهر اختصاصی Gemini (bubble کاربر / متن ساده پاسخ مدل) رندر می‌شوند.

---

## 4. Functional Requirements

| # | الزام |
|---|---|
| FR1 | تشخیص فرمت Gemini Takeout به‌صورت مجزا از فرمت‌های Claude/ChatGPT |
| FR2 | گروه‌بندی آیتم‌ها به مکالمات مجزا بر اساس شناسه داخل `details[0].url` |
| FR3 | بازسازی ترتیب زمانی صعودی، هم بین مکالمات، هم داخل هر مکالمه |
| FR4 | استخراج متن پیام کاربر از `title` با حذف پیشوند `"درخواست: "`؛ در نبود پیشوند، از کل `title` به‌عنوان fallback دفاعی استفاده شود (نه خطا) |
| FR5 | استخراج پاسخ(های) مدل از `safeHtmlItem`؛ در صورت وجود بیش از یک عضو، به‌عنوان لیست Draft مرتب نگه‌داری شود |
| FR6 | ساخت عنوان نمایشی مکالمه از اولین پیام کاربر همان مکالمه (کوتاه‌شده مطابق قاعده truncation موجود در سایر پلتفرم‌ها) |
| FR7 | Sanitize مستقیم HTML پاسخ مدل با DOMPurify پیش از رندر — بدون تبدیل به/از Markdown |
| FR8 | برای پیوست‌های بدون باینری، رندر Placeholder (آیکون + نام فایل) |
| FR9 | نادیده گرفتن فیلدهای بدون اطلاعات (`header`, `products`, `activityControls`) هنگام Parse |
| FR10 | نمایش تاریخ پیام با فرمت میلادی هم‌راستا با سایر پلتفرم‌ها |
| FR11 | در صورت وجود چند Draft، نمایش کنترل جابجایی بین Draftها روی پیام مدل |

## 5. Non-Functional Requirements

| # | الزام |
|---|---|
| NFR1 | Parser نباید در نبود فیلدهای اختیاری (`subtitles`, `attachedFiles`, `imageFile`, `safeHtmlItem` چندعضوی) خطا پرتاب کند — باید Graceful Degrade داشته باشد |
| NFR2 | Sanitization باید هرگونه script/event-handler را از HTML خارجی Gemini حذف کند (مرز امنیتی — این HTML داده‌ی غیرقابل‌اعتماد خارجی است) |
| NFR3 | گروه‌بندی/مرتب‌سازی باید با Takeout export‌های بزرگ (چند هزار آیتم Activity) بدون کندی محسوس در UI مقیاس‌پذیر باشد — مطابق الگوی مدیریت فایل بزرگ که برای Claude پیاده شده |

---

## 6. UI Behavior

- **پیام کاربر:** bubble راست‌چین تیره (مطابق اسکرین‌شات)
- **پیام مدل:** بدون bubble، متن ساده چپ‌چین با فرمت رندرشده (heading، لیست، bold، کد، خط جداکننده) — باید از نظر بصری با قراردادهای تایپوگرافی واقعی Gemini هم‌خوانی داشته باشد (مطابق مقیاس تایپ تعریف‌شده در `ui-context.md`)
- **Draft چندگانه:** کنترل کوچک (مثلاً "Draft 1/2" + دکمه قبلی/بعدی) فقط وقتی بیش از یک Draft وجود دارد رندر شود
- **Placeholder پیوست:** آیکون + نام فایل؛ بدون حالت تعاملی برای دانلود/پیش‌نمایش (خارج از scope این Unit)
- **آیتم لیست مکالمه:** عنوان مشتق‌شده + تاریخ (فرمت اپ‌وایدِ میلادی)

---

## 7. Validation

- فایلی که با schema مورد انتظار Gemini (الگوی `title` + `safeHtmlItem`) مطابقت ندارد، باید به مسیر شکست Format Detection موجود هدایت شود، نه خطای غیرقابل‌فهم
- `title` خالی → نمایش fallback هم‌راستا با سایر حالت‌های خالی موجود در اپ

## 8. Edge Cases

| # | سناریو |
|---|---|
| EC1 | مکالمه‌ای با فقط یک آیتم Activity (تک‌نوبته) |
| EC2 | آیتمی با ۲ عضو `safeHtmlItem` (تست کنترل Draft) |
| EC3 | آیتمی با پیوست کاربر (`attachedFiles` + `imageFile`)، بدون باینری واقعی |
| EC4 | آیتمی که مدل در آن تصویر تولید کرده (`attachedFiles` دارد، `imageFile` ندارد، `subtitles` حاوی «۱ تصویر تولید شد») |
| EC5 | `title` بدون پیشوند `"درخواست: "` (سناریوی دفاعی، در فیکسچر واقعی مشاهده نشده ولی باید safe باشد) |
| EC6 | پیام طولانی ترکیبی فارسی/انگلیسی (RTL+LTR) — باید از همان منطق تشخیص جهت پیاده‌شده برای Claude (Unit 09b) استفاده شود |
| EC7 | دو مکالمه با تاریخ نمایشی یکسان در لیست — بدون نیاز به Dedup، فقط نمایش لیستی است |

## 9. Acceptance Criteria

| # | معیار |
|---|---|
| AC1 | با فیکسچر واقعی (۲۳ آیتم / ۷ مکالمه)، دقیقاً ۷ مکالمه در بخش Gemini لیست پلتفرم‌ها نمایش داده شود |
| AC2 | ترتیب مکالمات و ترتیب پیام‌های داخل هر مکالمه، زمانی صعودی باشد |
| AC3 | در مکالمه‌ی دارای Draft دوگانه (سوال Export گرفتن)، کنترل جابجایی Draft نمایش داده شود و هر دو Draft قابل مشاهده باشند |
| AC4 | مکالمه‌ی دارای پیوست تصویر (گروه `b87b9155c31d54a7`)، هم برای jpg آپلودی کاربر و هم png تولیدشده توسط مدل، Placeholder نمایش دهد بدون Crash |
| AC5 | Parse کامل فیکسچر واقعی بدون خطای Console/Runtime انجام شود |
| AC6 | بازرسی دستی DOM نشان دهد هیچ script/event-handler اجراناپذیر باقی نمانده (تست Sanitization) |
| AC7 | محتوای ترکیبی RTL/LTR با جهت صحیح per-run رندر شود، مطابق الگوی تأییدشده برای Claude |
