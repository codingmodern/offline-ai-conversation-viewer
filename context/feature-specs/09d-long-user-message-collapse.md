# Spec اصلاحی: Unit 09d — جمع‌شدن پیام‌های طولانی کاربر (Show more/less)

> **مرجع:** رفتار مشاهده‌شده در claude.ai واقعی (عکس ضمیمه) — پیام طولانی کاربر بعد از چند خط جمع می‌شود با دکمه «Show more»
> **دامنه:** هر دو تم (`src/themes/claude/` و `src/themes/deepseek/`) — فقط حباب پیام **کاربر** (human)، نه پیام مدل
> **وابستگی:** بدون وابستگی به Unit های دیگر؛ مستقل قابل‌اجراست

---

## 1. Goal

جلوگیری از اشغال بیش‌ازحد فضای عمودی صفحه توسط پیام‌های طولانی کاربر (مثلاً پیست کردن لاگ چندصد خطی)، با جمع‌کردن حباب پیام بعد از یک آستانه‌ی مشخص و افزودن دکمه‌ی toggle «نمایش بیشتر / نمایش کمتر»، دقیقاً مطابق رفتار استاندارد claude.ai.

---

## 2. رفتار فعلی (Before)

حباب پیام کاربر صرف‌نظر از طول محتوا، همیشه **کامل و بدون محدودیت ارتفاع** رندر می‌شود؛ برای پیام‌های چندصدخطی (مثل پیست لاگ)، این باعث می‌شود صفحه‌ی مکالمه بیش‌ازحد کشیده و ناخوانا شود.

## 3. رفتار صحیح (After)

- اگر تعداد خطوط (یا ارتفاع محاسبه‌شده‌ی) محتوای حباب کاربر از **۶ خط** بیشتر باشد، حباب به‌صورت پیش‌فرض **جمع‌شده** نمایش داده می‌شود (فقط ۶ خط اول قابل مشاهده، با یک محوشدگی تدریجی (gradient fade) در پایین به‌جای برش ناگهانی).
- زیر محتوای جمع‌شده، یک دکمه‌ی متنی **«نمایش بیشتر»** ظاهر می‌شود.
- با کلیک، کل محتوا نمایش داده می‌شود و دکمه به **«نمایش کمتر»** تغییر می‌کند که با کلیک مجدد به حالت جمع‌شده برمی‌گردد.
- اگر محتوا ۶ خط یا کمتر بود، هیچ دکمه‌ای نمایش داده نمی‌شود — حباب کامل و بدون تغییر مثل قبل رندر می‌شود.

---

## 4. Functional Requirements

| # | نیازمندی |
|---|----------|
| FR1 | این رفتار فقط روی حباب پیام **کاربر** اعمال شود؛ پیام‌های assistant (که بدون حباب و تمام‌عرض هستند) تغییر نکنند |
| FR2 | آستانه‌ی جمع‌شدن: **۶ خط** محتوا (بر اساس ارتفاع محاسبه‌شده با `line-height` مشخص، نه شمارش دستی کاراکتر) |
| FR3 | حالت جمع‌شده باید یک افکت محوشدگی (gradient fade) در پایین محتوا داشته باشد تا برش محتوا ناگهانی/زشت به‌نظر نرسد |
| FR4 | دکمه‌ی toggle باید متن «نمایش بیشتر» / «نمایش کمتر» را متناسب با حالت فعلی نشان دهد |
| FR5 | این رفتار باید در **هر دو تم** (Claude و DeepSeek) به‌صورت یکسان (با توکن‌های رنگی مخصوص هر تم) پیاده‌سازی شود |
| FR6 | حالت باز/بسته باید state محلی هر پیام باشد (با تغییر پیام دیگر عوض نشود) و پیش‌فرض هر پیام طولانی، **جمع‌شده** باشد |

---

## 5. Validation

- پیام‌های کوتاه‌تر از آستانه نباید هیچ دکمه یا تغییر ظاهری داشته باشند (نه‌فقط دکمه مخفی، بلکه هیچ‌گونه`max-height`/overflow اضافه‌ای هم نباید اعمال شود که به کارایی رندر آسیب بزند).
- تشخیص «بیش از ۶ خط بودن» باید مستقل از زبان (فارسی/انگلیسی) و جهت متن (RTL/LTR) درست کار کند.
- این تغییر نباید با اصلاح قبلی `overflow-wrap: anywhere` / `min-width: 0` (که برای جلوگیری از سرریز افقی بود) تداخل کند — این یکی برای کنترل **ارتفاع (عمودی)** است، نه عرض.

---

## 6. Edge Cases

| سناریو | رفتار مورد انتظار |
|--------|---------------------|
| پیام دقیقاً ۶ خط | بدون جمع‌شدن، بدون دکمه (آستانه یعنی «بیشتر از ۶»، نه «۶ یا بیشتر») |
| پیام شامل یک بلوک کد یا خط بسیار طولانی بدون فاصله | باید همچنان طبق قوانین قبلی wrap شود؛ شمارش خط باید بعد از wrap شدن محاسبه شود، نه براساس تعداد `\n` خام |
| کاربر پیام رو باز می‌کند، بعد پیام جدیدی می‌فرستد | وضعیت باز/بسته‌ی پیام‌های قبلی حفظ شود، تغییر نکند |

---

## 7. Acceptance Criteria

- [ ] پیام‌های کاربر بلندتر از ۶ خط به‌صورت پیش‌فرض جمع‌شده نمایش داده می‌شوند
- [ ] دکمه‌ی «نمایش بیشتر/کمتر» به‌درستی toggle می‌کند
- [ ] افکت محوشدگی در لبه‌ی پایین محتوای جمع‌شده وجود دارد
- [ ] پیام‌های assistant تحت‌تاثیر این تغییر قرار نمی‌گیرند
- [ ] رفتار در هر دو تم (Claude و DeepSeek) یکسان پیاده‌سازی شده
- [ ] پیام‌های کوتاه بدون تغییر ظاهری باقی می‌مانند
- [ ] `npm run test` / `lint` / `build` بدون خطای جدید پاس می‌شوند

---

## 8. یادداشت برای Cline

قبل از پیاده‌سازی:
1. بررسی کن آیا تشخیص «بیش از ۶ خط» بهتره با CSS خالص (`-webkit-line-clamp` + اندازه‌گیری `scrollHeight` در JS برای تصمیم نمایش دکمه) انجام بشه یا با شمارش خط در سطح داده. پیشنهاد استاندارد: **CSS `line-clamp` برای جلوه‌ی بصری + یک بررسی `scrollHeight > clientHeight` در component mount برای تصمیم نمایش/عدم‌نمایش دکمه.**
2. گزارش بده و پیشنهاد بده، قبل از هرگونه تغییر کد.
