# Feature Spec: Platform Auto-Detection

> **Unit:** 02 — Platform Auto-Detection
> **Depends on:** Unit 01 (Import & Validation) — دریافت فایل JSON از قبل Validate‌شده (فقط از نظر نحوی و غیرخالی‌بودن؛ بدون هیچ بررسی مربوط به تشخیص پلتفرم)
> **Maps to Feature:** #2 در فهرست Featureهای تأییدشده

---

## Goal

تشخیص کاملاً خودکار پلتفرم مبدا (ChatGPT / Claude / Gemini / DeepSeek) یک فایل JSON Validate‌شده، بدون هیچ دخالت یا انتخاب دستی از سوی کاربر، و هدایت آن به Parser صحیح در مرحله‌ی بعد (Unit 03) — یا رد فایل با پیام مشخص در صورت عدم تطابق با هیچ فرمت شناخته‌شده.

> **مرز مسئولیت:** این واحد تنها و یگانه مرجع تصمیم‌گیری درباره‌ی «آیا این فایل متعلق به یک پلتفرم پشتیبانی‌شده است یا نه» است. Unit 01 هیچ بررسی مشابهی انجام نمی‌دهد.

---

## User Flow

1. فایل JSON Validate‌شده (خروجی Unit 01) وارد Pipeline تشخیص می‌شود.
2. سیستم به‌صورت داخلی، ساختار فایل را در برابر امضای (Signature) هر پلتفرم ثبت‌شده در Registry مرکزی بررسی می‌کند.
3. هر پلتفرم ثبت‌شده تابع `detect()` خودش را روی داده اجرا می‌کند تا مشخص شود آیا ساختار با آن پلتفرم مطابقت دارد یا نه.
4. اگر دقیقاً یک پلتفرم تطابق مثبت داشت → پلتفرم شناسایی‌شده مشخص و فایل + شناسه‌ی پلتفرم به Unit 03 (Modular Parsing System) منتقل می‌شود.
5. اگر هیچ پلتفرمی تطابق نداشت → خطای `UnsupportedFormatError` بازگردانده و به کاربر پیام «فرمت فایل پشتیبانی نمی‌شود» نمایش داده می‌شود.
6. اگر بیش از یک پلتفرم هم‌زمان تطابق مثبت داد (تناقض Detection) → طبق اصل «رفتار محصول اختراع نکن» (`ai-workflow-rules.md` بخش ۳)، این وضعیت به‌عنوان خطای داخلی گزارش و به‌صورت شکست ایمن (Fail Safe) مدیریت می‌شود؛ کاربر پیام عمومی «فرمت فایل قابل تشخیص قطعی نیست» می‌بیند.
7. کل فرآیند بدون هیچ نمایش UI برای انتخاب دستی پلتفرم انجام می‌شود (طبق Invariant #4 پروژه).

## Functional Requirements

| # | Requirement |
|---|-------------|
| FR1 | سیستم باید یک Registry مرکزی داشته باشد که تمام ماژول‌های `parsers/{provider}/` ثبت‌شده را نگه می‌دارد. **این Registry واحد است** — همین Registry در Unit 03 نیز برای بازیابی تابع `parse()` همان ماژول استفاده می‌شود؛ هیچ Registry جداگانه‌ی دومی برای لایه‌ی Parsing تعریف نمی‌شود |
| FR2 | تشخیص باید صرفاً بر پایه‌ی بررسی ساختار داده (کلیدها، شکل Object/Array، الگوهای خاص هر پلتفرم) انجام شود، نه نام فایل یا پسوند |
| FR3 | هر ماژول `parsers/{provider}/` باید تابع `detect(rawJson: unknown): boolean` را Export کند (طبق قرارداد `code-standards.md`) |
| FR4 | Registry باید به ترتیب مشخص و قابل‌پیش‌بینی، `detect()` هر پلتفرم را فراخوانی کند |
| FR5 | در صورت تطابق مثبت دقیقاً یک پلتفرم، شناسه‌ی همان پلتفرم (مثلاً `'chatgpt'`) به همراه داده‌ی خام JSON به مرحله‌ی بعد (Unit 03) ارسال شود |
| FR6 | در صورت عدم تطابق هیچ پلتفرمی، خطای دسته‌بندی‌شده (`UnsupportedFormatError`) بازگردانده شود |
| FR7 | در صورت تطابق هم‌زمان چند پلتفرم، این حالت به‌عنوان خطای Detection (نه انتخاب خودکار اولین مورد) گزارش شود — تشخیص مبهم نباید بی‌سروصدا حل شود |
| FR8 | افزودن یک پلتفرم جدید به Registry نباید نیازمند تغییر در منطق Detection پلتفرم‌های موجود باشد (طبق Invariant #3) |
| FR9 | هیچ UI یا مسیر تعاملی برای انتخاب/Override دستی پلتفرم توسط کاربر وجود نداشته باشد |

---

## Non-Functional Requirements

| # | Requirement |
|---|-------------|
| NFR1 | Detection باید سریع باشد (در حد میلی‌ثانیه) و در همان Web Worker مرحله‌ی Import ادامه یابد، بدون Round-trip اضافه به Main Thread |
| NFR2 | منطق Detection هر پلتفرم باید کاملاً مستقل و بدون وابستگی متقاطع به Detection پلتفرم‌های دیگر باشد (طبق Invariant #3) |
| NFR3 | Registry باید به‌گونه‌ای طراحی شود که افزودن پلتفرم جدید فقط شامل «ثبت» یک تابع `detect()` جدید باشد، نه تغییر ساختار Registry |

## UI Behavior

| وضعیت | نمایش |
|-------|-------|
| **در حال تشخیص** | ادامه‌ی همان نشانگر Progress مرحله‌ی Import (Unit 01)؛ Detection از دید کاربر بخشی نامرئی از همان فرآیند Import است، نه یک مرحله‌ی جدا با UI مستقل |
| **تشخیص موفق** | بدون نمایش پیام مجزا به کاربر — فایل به‌سادگی وارد مرحله‌ی Parsing (Unit 03) می‌شود و در نهایت با آیکون/Theme همان پلتفرم در کتابخانه ظاهر خواهد شد (خروجی نهایی در Unit 04) |
| **فرمت ناشناخته** | پیام خطای کاربرپسند: «این فایل به هیچ‌کدام از پلتفرم‌های پشتیبانی‌شده (ChatGPT، Claude، Gemini، DeepSeek) تعلق ندارد» |
| **تشخیص مبهم (چند تطابق)** | پیام خطای کاربرپسند عمومی: «فرمت فایل قابل تشخیص قطعی نیست»؛ جزئیات فنی (کدام Parserها تطابق دادند) فقط از طریق Internal diagnostic logging ثبت می‌شود، نه در UI |

> هیچ حالت UI برای «انتخاب پلتفرم توسط کاربر» تعریف نشده و نباید در پیاده‌سازی اضافه شود.

## Validation

| بررسی | نحوه‌ی اعمال |
|-------|----------------|
| **اجرای `detect()` هر پلتفرم** | هر ماژول Parser مسئول اعتبارسنجی ساختار خودش است؛ بدون فرض مشترک بین پلتفرم‌ها |
| **تعداد تطابق‌ها** | باید دقیقاً برابر ۱ باشد؛ ۰ یا بیش از ۱ هر دو حالت خطا محسوب می‌شوند |
| **بدون اعتماد به فراداده‌ی فایل** | نام فایل، پسوند، یا هر متادیتای سیستم فایل در تصمیم Detection نقشی ندارد؛ فقط محتوای JSON بررسی می‌شود |

## Edge Cases

| سناریو | رفتار موردانتظار |
|--------|-------------------|
| فایل دقیقاً با ساختار یکی از ۴ پلتفرم مطابقت دارد | تشخیص موفق، انتقال به Unit 03 با شناسه‌ی پلتفرم صحیح |
| فایل با هیچ‌کدام از پلتفرم‌های ثبت‌شده مطابقت ندارد (شامل JSON معتبر اما کاملاً بی‌ربط، مثلاً یک آرایه‌ی اعداد) | `UnsupportedFormatError`؛ فایل رد می‌شود |
| فایل ساختاری شبیه به دو پلتفرم هم‌زمان دارد (مثلاً به‌دلیل شباهت فرمت‌های صادرشده) | خطای Detection مبهم؛ فایل رد می‌شود؛ گزارش فنی (کدام پلتفرم‌ها) فقط از طریق Internal diagnostic logging |
| فرمت رسمی یک پلتفرم در آینده تغییر کند و دیگر با `detect()` فعلی تطابق نداشته باشد | فایل به‌عنوان `UnsupportedFormatError` رد می‌شود (رفتار امن پیش‌فرض)؛ به‌روزرسانی امضای Detection آن پلتفرم به‌صورت جداگانه در همان ماژول `parsers/{provider}/` انجام می‌شود، بدون تأثیر بر پلتفرم‌های دیگر |
| فایل خیلی شبیه یک پلتفرم است اما یک فیلد کلیدی جا افتاده (نسخه‌ی ناقص Export) | بسته به سخت‌گیری امضای `detect()` آن پلتفرم؛ اگر امضا فیلد را الزامی بداند → `UnsupportedFormatError`؛ این رفتار در سطح هر Parser به‌طور مستقل تعریف می‌شود، نه در این Spec |

## Acceptance Criteria

- [ ] all currently registered providers (هر Provider ثبت‌شده در Registry) با فایل نمونه‌ی واقعی خودش به‌درستی و بدون خطا تشخیص داده می‌شود
- [ ] فایل با ساختار ناشناخته با پیام «فرمت پشتیبانی نمی‌شود» رد می‌شود
- [ ] در صورت تطابق مبهم (چند پلتفرم)، فایل رد می‌شود و خطای مشخصی گزارش می‌شود (نه انتخاب خودکار اولین مورد)
- [ ] هیچ نقطه‌ای از UI امکان انتخاب دستی پلتفرم را به کاربر نمی‌دهد
- [ ] افزودن یک `detect()` جدید به Registry هیچ تغییری در کد Detection پلتفرم‌های موجود ایجاد نمی‌کند
- [ ] Detection کاملاً در Web Worker (ادامه‌ی جریان Unit 01) انجام می‌شود، بدون Block شدن UI
- [ ] Registry معرفی‌شده در این واحد همان Registry‌ای است که Unit 03 برای بازیابی `parse()` استفاده می‌کند — بدون Registry موازی
