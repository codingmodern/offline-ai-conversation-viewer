# Feature Spec: Authentic Multi-Theme Rendering

> **Unit:** 06 — Authentic Multi-Theme Rendering
> **Depends on:** Unit 04 (Local Chat Library) — دریافت مکالمه‌ی انتخاب‌شده و شناسه‌ی پلتفرم آن
> **Maps to Feature:** #6 در فهرست Featureهای تأییدشده

---

## Goal

نمایش محتوای مکالمه‌ی انتخاب‌شده با ظاهر بصری اختصاصی همان پلتفرم (Layout، رنگ، تایپوگرافی، حباب پیام، آیکون)، مطابق مشخصات هر پلتفرم در `ui-context.md`، به‌گونه‌ای که هر پلتفرم از سه پلتفرم دیگر از نظر بصری کاملاً قابل‌تشخیص باشد و هیچ کد یا Asset رسمی از هیچ پلتفرم استفاده نشود.

> **مرز مسئولیت:** این واحد مسئول **رندر بصری** محتوای مکالمه است — یعنی نمایش صحیح ظاهر هر پلتفرم بر اساس داده‌ی از قبل موجود. منبع داده (کدام مکالمه، کدام پیام‌ها) از Unit 04 تأمین می‌شود. هرگونه رفتار تعاملی روی پیام‌ها به‌جز **دکمه‌ی Copy** (که به‌صراحت در `ui-context.md` §4.6 به‌عنوان تنها Action فعال پیام تأیید شده و طبق ADR #21 هم روی پیام کاربر و هم روی پیام مدل فعال است) خارج از Scope این واحد است؛ اجرای کد، Regenerate، Like/Dislike و رفتارهای مشابه پیاده‌سازی نمی‌شوند.

---

## User Flow

1. کاربر یک مکالمه را در Sidebar کتابخانه (Unit 04) انتخاب می‌کند.
2. سیستم بر اساس پلتفرم ثبت‌شده‌ی همان مکالمه، ظاهر بصری متناظر با همان پلتفرم را رندر می‌کند (مطابق مشخصات هر پلتفرم در `ui-context.md` → بخش ۴).
3. کاربر مکالمه‌ی دیگری (از پلتفرمی متفاوت) را انتخاب می‌کند؛ ناحیه‌ی نمایش بدون رفرش کامل صفحه به ظاهر پلتفرم جدید تغییر می‌کند.

## Functional Requirements

| # | Requirement |
|---|-------------|
| FR1 | ظاهر بصری نمایش‌داده‌شده برای هر مکالمه باید مطابق مشخصات مستندشده‌ی همان پلتفرم در `ui-context.md` باشد (Layout، پالت رنگی، تایپوگرافی، الگوی حباب پیام، آیکون‌ها) |
| FR2 | تعویض مکالمه‌ی انتخاب‌شده بین دو پلتفرم مختلف باید ظاهر بصری را به‌طور کامل و صحیح تغییر دهد، بدون رفرش کامل صفحه |
| FR3 | هیچ کد، فونت غیرمجاز، یا Asset رسمی (لوگو، آیکون برند) از هیچ پلتفرم به‌طور مستقیم استفاده یا کپی نمی‌شود (طبق Invariant #6 در `architecture.md`) |
| FR4 | پیام‌های کاربر و پاسخ مدل باید طبق الگوی بصری تعریف‌شده‌ی همان پلتفرم (حباب/بدون‌حباب، Alignment، آواتار) از هم قابل‌تمایز باشند |
| FR5 | افزودن پشتیبانی بصری یک پلتفرم جدید نباید نیازمند تغییر در ظاهر پلتفرم‌های موجود باشد (طبق Invariant #3 در `architecture.md`) |
| FR6 | محتوای ساختاریافته‌ی پیام (مانند بلوک کد) باید با ظاهر متناسب با همان پلتفرم نمایش داده شود؛ فقط نمایش بصری مدنظر است، نه هیچ رفتار تعاملی |
| FR7 | **متن پاسخ مدل (assistant text، به‌جز بلوک کدِ fenced) باید از طریق Markdown رندر شود**، نه به‌صورت Verbatim/raw — یعنی ساختارهای استاندارد Markdown (heading، emphasis، لیست، blockquote، لینک/Autolink، خط خالی) به HTML تبدیل می‌شوند، در حالی‌که سطر XSS در `architecture.md` با sanitize کردن خروجی رعایت می‌شود (ADR #21). پیام‌های کاربر همچنان Verbatim رندر می‌شوند (سفیدبود متن کاربر یک تصمیم حفظ‌شده است) |

## Non-Functional Requirements

| # | Requirement |
|---|-------------|
| NFR1 | رنگ و کنتراست ظاهر هر پلتفرم باید حداقل استاندارد Accessibility تعریف‌شده در `ui-context.md` → بخش ۶ را رعایت کند |
| NFR2 | تعویض ظاهر بین دو مکالمه‌ی پلتفرم متفاوت نباید تأخیر محسوس ایجاد کند |
| NFR3 | ظاهر هر پلتفرم باید مستقل از ظاهر پلتفرم‌های دیگر توسعه‌پذیر باشد؛ تغییر ظاهر یک پلتفرم نباید ظاهر پلتفرم دیگر را تحت تأثیر قرار دهد |

## UI Behavior

| وضعیت | نمایش |
|-------|-------|
| **نمایش مکالمه‌ی یک پلتفرم مشخص** | ناحیه‌ی نمایش مکالمه مطابق مشخصات همان پلتفرم در `ui-context.md` (بخش ۴.۳ تا ۴.۶) رندر می‌شود |
| **سوییچ بین مکالمات پلتفرم‌های مختلف** | ظاهر بصری بدون پرش ناخواسته یا حالت میانی نامعتبر تغییر می‌کند |
| **Responsive Behavior** | مطابق جدول «Responsive Behavior» تعریف‌شده برای همان پلتفرم در `ui-context.md` |

> نمایش حالت Light/Dark هر پلتفرم از تنظیم کلی حالت نمایش اپلیکیشن (طبق `ui-context.md` → بخش ۲، Shell UI Theme) پیروی می‌کند. این واحد تنظیم مستقل یا کنترل جداگانه‌ای برای Light/Dark هر پلتفرم معرفی نمی‌کند.

## Validation

| بررسی | نحوه‌ی اعمال |
|-------|----------------|
| **تطابق ظاهر اعمال‌شده با پلتفرم مکالمه** | ظاهر رندرشده باید همیشه با پلتفرم واقعی همان مکالمه (طبق تشخیص Unit 02) یکی باشد؛ هیچ‌گاه ظاهر اشتباه یا یک ظاهر پیش‌فرض عمومی روی مکالمه‌ی یک پلتفرم شناخته‌شده اعمال نمی‌شود |

## Edge Cases

| سناریو | رفتار موردانتظار |
|--------|-------------------|
| مکالمه‌ای با نوع پیام یا نقش پیام غیرمعمول (طبق Edge Case مطرح‌شده در Unit 03) | این واحد باید بتواند چنین پیامی را بدون Crash رندر کند، حتی اگر ظاهر آن ساده‌شده یا عمومی باشد |
| مکالمه‌ی خالی (بدون پیام) | ناحیه‌ی نمایش با ظاهر صحیح پلتفرم رندر می‌شود، اما بدون هیچ پیامی؛ رندر خالی خطا محسوب نمی‌شود |
| سوییچ سریع و متوالی بین چند مکالمه از پلتفرم‌های مختلف | هر سوییچ باید ظاهر صحیح متناظر با همان مکالمه را نمایش دهد، بدون باقی ماندن اثر بصری از حالت قبلی |
| محتوای پیام حاوی بلوک کد یا عناصر ساختاریافته (طبق مشخصات Artifact/Canvas هر پلتفرم در `ui-context.md`) | نمایش بصری این عناصر مطابق الگوی مستندشده‌ی همان پلتفرم انجام می‌شود؛ بدون هیچ رفتار تعاملی یا زنده |
| متن پاسخ مدل حاوی Markdown استاندارد (heading، emphasis، لیست، blockquote، لینک/Autolink، خط خالی) | رندر از طریق marked → DOMPurify (sanitize) انجام می‌شود؛ پیام‌های کاربر همچنان Verbatim رندر می‌شوند (FR7، ADR #21) |

## Acceptance Criteria

- [ ] برای یک مکالمه‌ی هر یک از پلتفرم‌های پشتیبانی‌شده، ناحیه‌ی نمایش از نظر ظاهری با نمونه‌ی مستندشده‌ی همان پلتفرم در `ui-context.md` مطابقت قابل‌مشاهده دارد
- [ ] انتخاب دو مکالمه از دو پلتفرم متفاوت به‌ترتیب، دو ظاهر بصری قابل‌تشخیص از یکدیگر تولید می‌کند
- [ ] هیچ فایل، متن، یا کامنت در کد پروژه حاوی کپی مستقیم Asset رسمی (لوگو، فونت اختصاصی غیرمجاز) هیچ پلتفرم نیست
- [ ] افزودن پشتیبانی بصری یک پلتفرم جدید هیچ تغییری در فایل‌های ظاهری پلتفرم‌های موجود ایجاد نمی‌کند
- [ ] رندر یک مکالمه‌ی خالی یا دارای نقش پیام غیرمعمول، خطا یا Crash ایجاد نمی‌کند
- [ ] تغییر مکالمه‌ی انتخاب‌شده باعث رفرش کامل صفحه نمی‌شود
