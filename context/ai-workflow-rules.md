## 2. Development Approach

### Methodology

| Aspect | Approach |
|--------|----------|
| **Development Method** | Spec-driven، گام‌به‌گام (Step-by-step) |
| **Build Order** | افزایشی — یک واحد Spec در هر زمان |
| **Scope Discipline** | کار روی یک واحد تا تکمیل کامل؛ بدون پرش به واحد بعدی |
| **Spec-Driven** | فایل‌های Context (`architecture.md`, `ui-context.md`, ...) چیستی را تعریف می‌کنند؛ Feature Specها چگونگی را |

### Scoping Rules

- **کار روی یک واحد ویژگی در هر زمان.** بدون تغییرات حدسی خارج از Scope واحد جاری.
- **افزایش‌های کوچک و قابل‌تأیید** به‌جای تغییرات بزرگ همه‌باهم.
- **عدم ترکیب مرزهای سیستمی نامرتبط در یک گام** — مثلاً تغییر Parser و تغییر Theme در یک Commit ترکیب نشود؛ حتی در معماری بدون بک‌اند، لایه‌های `parsers/`, `storage/`, `themes/`, `components/` باید مجزا توسعه یابند.

### When to Split Work

اگر یک گام پیاده‌سازی شامل موارد زیر باشد، باید تقسیم شود:

- تغییر هم‌زمان در بیش از یک لایه‌ی معماری (مثلاً `parsers/` + `themes/` + `storage/` در یک گام)
- افزودن بیش از یک Parser یا Theme جدید در یک گام
- رفتاری که در فایل‌های Context به‌وضوح تعریف نشده
- تغییری که نمی‌توان آن را در کمتر از ۵ دقیقه End-to-End تست کرد (مثلاً باز کردن یک فایل نمونه و بررسی رندر صحیح)

## 3. Handling Missing / Ambiguous Requirements

| Situation | Action |
|-----------|--------|
| نیازمندی مبهم است | قبل از پیاده‌سازی، در فایل Context مربوطه حل شود |
| نیازمندی کاملاً غایب است | به‌عنوان **Open Question** در `progress-tracker.md` اضافه شود قبل از ادامه |
| نیازمندی با یک Invariant موجود (`architecture.md` → بخش ۶) تناقض دارد | توقف. تناقض را گزارش کن. تا حل نشدن ادامه نده |
| Edge Case مستند نشده کشف شد | به `architecture.md` → «Constraints & Edge Cases» اضافه شود، سپس مدیریت شود |
| ساختار JSON یک پلتفرم نامشخص/متفاوت از انتظار است | قبل از نوشتن Parser، نمونه واقعی فایل Export بررسی و ساختار در Fixture مستند شود (`tests/fixtures/{provider}/`) |

**رفتار محصول اختراع نکن.** اگر درباره‌ی یک تصمیم طراحی مطمئن نیستی، پیش از ادامه در بخش Open Questions بپرس.

## 4. Verification & Quality Gates

### Pre-Commit Checklist

قبل از علامت‌گذاری هر واحد به‌عنوان تکمیل‌شده، موارد زیر را بررسی کن:

1. [ ] واحد جاری در محدوده‌ی تعریف‌شده‌ی خودش End-to-End کار می‌کند
2. [ ] هیچ Invariant تعریف‌شده در `architecture.md` نقض نشده (به‌ویژه: بدون درخواست شبکه، جداسازی کامل Parserها، Sanitize محتوا، تشخیص کاملاً خودکار پلتفرم)
3. [ ] تمام Acceptance Criteria این واحد برآورده شده
4. [ ] ورودی خارجی (فایل JSON) در مرز ورود (`parsers/`) Validate می‌شود
5. [ ] پیام‌های خطا کاربرپسند هستند و جزئیات فنی خام نمایش داده نمی‌شود (طبق «Error Handling Standards» در `code-standards.md`)
6. [ ] `progress-tracker.md` وضعیت کار انجام‌شده را منعکس می‌کند
7. [ ] `npm run build` (Vite) بدون خطا اجرا می‌شود
8. [ ] تست‌ها با `npm run test` (Vitest) پاس می‌شوند
9. [ ] Linter (ESLint) بدون هیچ Warning پاس می‌شود
10. [ ] مستندات در صورت تغییر رفتار به‌روزرسانی شده‌اند
11. [ ] Import‌ها از Alias `@/` استفاده می‌کنند (طبق `code-standards.md`)، بدون Relative عمیق (`../../../`)

### Before Moving to the Next Unit

1. واحد جاری کاملاً طبق چک‌لیست بالا تأیید شده
2. تمام تغییرات با پیام Commit مطابق Conventional Commits ثبت شده‌اند
3. در صورت نیاز، Branch به Remote Push شده است

## 5. Collaboration Mode

| Aspect | Setting |
|--------|---------|
| **Style** | Expert — اولویت با اجرا و پیاده‌سازی، نه توضیح |
| **Pace** | سریع، با حداقل توضیحات کلامی |
| **Code Review** | بله — پیش از Merge، درخواست بازبینی |
| **Error Handling** | در صورت گیر کردن — توقف، توضیح دقیق مانع + پیشنهاد راه‌حل |

### Response Format Guidelines

هنگام پیاده‌سازی:

- **اولویت با پیاده‌سازی است، نه توضیح.** پاسخ‌ها مستقیم سراغ کد/تغییر می‌روند.
- **توضیح تصمیمات معماری فقط در دو حالت ارائه شود:** ۱) وقتی تصمیم واقعاً مهم است (مثلاً تغییر روی یک Invariant، انتخاب بین چند راه‌حل معتبر — طبق بخش ۱۰)، یا ۲) وقتی صراحتاً درخواست شود.
- پاسخ‌های پیاده‌سازی **مختصر و متمرکز** باشند؛ بدون مقدمه‌چینی یا توضیح گام‌به‌گام غیرضروری.
- در صورت بروز خطا، همچنان توضیح بده: (الف) چه اتفاقی افتاد، (ب) چرا افتاد، (ج) چگونه رفع می‌شود — این استثنا باقی می‌ماند چون برای رفع مشکل ضروری است.
- وقتی یک واحد تکمیل شد، چک‌لیست تأیید را اجرا و نتایج را **به‌صورت خلاصه** گزارش کن.

## 6. Protected Files

فایل‌های زیر بدون دستور صریح تغییر نکنند:

- `themes/*/tokens.css` — فقط بعد از تأیید مقادیر نهایی در `ui-context.md` تغییر کنند، نه به‌صورت حدسی در حین کدنویسی Component
- `types/` (مدل‌های داده‌ی مشترک) — تغییر در `UnifiedConversation` یا `ParseError` باید ابتدا در `architecture.md` منعکس شود
- `node_modules/`, `package-lock.json` — فایل‌های قفل (افزودن پکیج فقط از طریق CLI)
- هر بخش داخلی کتابخانه‌ی شخص ثالث (مثلاً Dexie، React)
- فایل‌های پیکربندی ابزارهایی که هنوز مستند نشده‌اند (مثلاً تنظیمات CI) مگر Spec آن را الزامی کند

## 7. Keeping Docs in Sync

فایل Context مربوطه را هر بار که پیاده‌سازی چیزی را تغییر می‌دهد به‌روزرسانی کن:

- **معماری سیستم یا مرزهای ماژول‌ها (`parsers/`, `themes/`, `storage/`, ...)** → به‌روزرسانی `architecture.md`
- **تصمیمات مدل ذخیره‌سازی (Schema Dexie)** → به‌روزرسانی `architecture.md`
- **قراردادهای کد یا استانداردها** → به‌روزرسانی `code-standards.md`
- **Scope ویژگی‌ها** → به‌روزرسانی `project-overview.md`
- **تصمیمات طراحی بصری (رنگ، تایپوگرافی، الگوی هر Theme)** → به‌روزرسانی `ui-context.md`
- **پیشرفت، گام‌های بعدی، تصمیمات** → به‌روزرسانی `progress-tracker.md`

> **قانون:** اگر پیاده‌سازی چیزی را که در یک فایل Context مستند شده تغییر دهد، فایل باید **قبل از ادامه‌ی کار** به‌روزرسانی شود. اجازه نده مستندات از کد عقب بماند.

## 8. Commit Convention

از Conventional Commits استفاده کن:

| Prefix | زمان استفاده |
|--------|------|
| `feat:` | یک ویژگی جدید |
| `fix:` | رفع باگ |
| `chore:` | نگهداری، وابستگی‌ها، ابزار |
| `docs:` | فقط مستندات |
| `refactor:` | تغییر کد بدون رفع باگ یا افزودن ویژگی |
| `test:` | افزودن یا به‌روزرسانی تست |
| `style:` | فرمت‌بندی، بدون تغییر کد Production |

مثال: `feat: add ChatGPT parser and detection module`

## 9. Adding a New Provider (راهنمای گسترش پروژه)

> این بخش مختص این پروژه است و از الگوی Modular Parsing System (`architecture.md`) نشات می‌گیرد.

برای افزودن پشتیبانی از یک پلتفرم AI جدید، این گام‌ها به ترتیب و **هرکدام به‌عنوان یک واحد کاری مجزا** انجام شوند:

1. مستندسازی مشخصات بصری پلتفرم در `ui-context.md` (بخش ۴) — تأیید کاربر قبل از کدنویسی
2. افزودن پوشه‌ی Parser جدید در `parsers/{provider}/` با پیاده‌سازی `detect()` و `parse()`
3. ثبت Parser جدید در Registry مرکزی `detection/`
4. افزودن Fixture (نمونه فایل JSON واقعی/Anonymized) در `tests/fixtures/{provider}/`
5. نوشتن Unit Test برای Detection و Parsing
6. افزودن پوشه‌ی Theme جدید در `themes/{provider}/` مطابق ساختار Token تعریف‌شده در `ui-context.md`
7. تست End-to-End: باز کردن نمونه فایل → مشاهده‌ی صحیح در کتابخانه و رندر Theme

هیچ‌کدام از این گام‌ها نباید کد Parser یا Theme پلتفرم‌های موجود را تغییر دهد (طبق Invariant #3 در `architecture.md`).

## 10. AI Decision Rules

> این قوانین رفتار تصمیم‌گیری مدل هوش مصنوعی در طول توسعه‌ی این پروژه را کنترل می‌کنند و بر تمام بخش‌های بالا اولویت دارند.

- **هرگز نیازمندی پروژه اختراع نکن.** اگر چیزی در فایل‌های Context تعریف نشده، طبق بخش ۳ به‌عنوان Open Question مطرح شود.
- **هرگز معماری تأییدشده را بدون اجازه‌ی من تغییر نده.** هر تغییری در `architecture.md` نیازمند تأیید صریح است.
- **هرگز مشخصات تأییدشده را تغییر نده مگر صراحتاً درخواست شود** — این شامل `project-overview.md`, `ui-context.md`, `code-standards.md`, و هر Feature Spec تأییدشده می‌شود.
- **قبل از ساخت Component یا Utility جدید، ابتدا از وجود نمونه‌ی قابل‌استفاده‌ی موجود مطمئن شو** و آن را دوباره استفاده کن.
- **سازگاری (Consistency) را بر بهینه‌سازی (Optimization) ترجیح بده** — الگوی موجود در پروژه را دنبال کن، حتی اگر راه‌حل «بهینه‌تر»ی به ذهن برسد؛ بهینه‌سازی فقط با تأیید صریح انجام شود.
- **اگر چند راه‌حل معتبر وجود دارد**، به‌طور خلاصه Trade-off هرکدام را توضیح بده و پیش از انتخاب، منتظر تأیید من بمان.
- **هرگز ویژگی اضافه خارج از Scope تأییدشده‌ی فعلی اضافه نکن** — حتی اگر مفید یا بدیهی به‌نظر برسد.
- **فایل‌های Context را به‌عنوان تنها منبع حقیقت (Single Source of Truth) دنبال کن** — در صورت تناقض بین حافظه/فرض و فایل‌های Context، فایل‌های Context اولویت دارند.
- **پیش از افزودن هر Dependency، پکیج، کتابخانه، فریم‌ورک، الگوی معماری جدید، یا Refactor بزرگ که در فایل‌های Context تأیید نشده، توقف کن و ابتدا تأیید بگیر.** فناوری جدید را پیش‌دستانه اضافه یا جایگزین نکن (مثلاً افزودن یک کتابخانه‌ی State Management جدید، تعویض Dexie با راه‌حل دیگر، یا تغییر الگوی Parser Registry بدون تأیید صریح مجاز نیست).
